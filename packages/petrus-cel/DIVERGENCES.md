# petrus-cel: divergences from the Python reference

The contract is cel-python's (`celpy` 0.5.0) observable behaviour on every
expression a Petrus net can carry, and `petrus.impetus.binding.cel`'s
environments on top of it (pinned reference: `upstream/petrus` 3f85fc2).
That behaviour covers parse trees and parse errors, values with their
`repr` and truthiness, and raised exceptions rendered whole: class,
arguments and `repr()`. Where cel-python departs from the CEL specification,
this package follows cel-python; the module documentation of `Petrus.Cel`
lists those departures, and the differential corpus records each one. Those
are not divergences.

The differential corpus replays all of its expressions with no exclusion.
The divergences left are the ones listed under "Open" below; item 9 can be
reached from a realistic net, and none of the others can. Item 8, under "By
design", can be reached too, but it is not a gap: there the port follows the
specification where the reference crashes.

## API shape

These change how a Haskell caller holds the library, not what an expression
evaluates to.

- **Exceptions are values.** celpy raises `CELParseError`,
  `CELEvalError` and Python exceptions. `compile` returns
  `Either ParseError Program`, and `evaluateJson`/`evaluateValues` return
  `Either Exc Value`, where `Exc` is a CEL evaluation error (`CelExc`) or a
  Python exception (`PyExc`) carrying the class name and arguments celpy's
  rendering shows. Nothing is thrown.
- **Compile, then evaluate.** celpy's `Environment().compile(text)` →
  `env.program(ast)` → `program.evaluate(activation)` is `compile` (a pure
  parse to a typed tree) and `evaluateJson program variables`. The
  activation is a list of `(name, Json)` pairs converted as celpy's
  `json_to_cel` would; `evaluateValues` takes values that are already CEL
  values.

## Resolved

### 1. A string literal spelling a lone surrogate

`'\uD800'` is a valid CEL string literal, and cel-python keeps it as a
Python `str` holding the lone surrogate.

Before the audit's IMP-2 and IMP-7, `Data.Text` could not hold a surrogate,
so the Haskell lexer decoded such a literal to U+FFFD. Three things changed
because of that: the value's `repr` (`'�'` against `'\ud800'`), its
equality with other strings, and the errors cel-python raises when it
encodes the string. The corpus runner excluded the one recorded case,
`'\uD800'`.

This is now resolved. The lexer builds literals with
`Petrus.Json.Wtf8.fromCodePoints`, the same WTF-8 representation
`petrus-json` uses for lone surrogates in JSON strings (IMP-2). The literal
keeps its surrogate, and size, concatenation, comparison and `repr` agree
with CPython.

Where cel-python encodes a string to UTF-8, CPython raises
`UnicodeEncodeError`, and `Petrus.Cel.Ops.encodeUtf8Strict` raises the same
error with the same arguments. These places are:

- `bytes(s)`;
- both the pattern and the text of `matches`.

Evidence:

- the corpus group `literal.string.surrogates` (18 expressions), with no
  case skipped;
- the "lone-surrogate strings" example in `test/Properties.hs`, which checks
  all of the exception's arguments as celpy renders them.

### 1b. `string(bytes)` of undecodable bytes

`string(b'...')` decodes UTF-8 strictly, and CPython raises
`UnicodeDecodeError` with the arguments `(encoding, object, start, end,
reason)` for the first malformed sequence. The package's own decoder
reported one byte in its message (`can't decode byte 0xe2 in position 0`)
where CPython names a range (`can't decode bytes in position 0-1`), and gave
the exception the message as its only argument, so celpy's rendering
differed.

This is now resolved: `Petrus.Cel.Ops.decodeUtf8` takes the failure from
petrus-json's `Petrus.Json.Python.Decode.utf8DecodeFailure` (checked against
the pinned interpreter on generated bytes) and raises the error with
CPython's arguments.

Evidence: the "undecodable bytes" example in `test/Properties.hs`, whose
expected texts are celpy's own (`string(b'\xff')`, `string(b'\xe2\x82')`,
`string(b'\xe2\x82A')`, `string(b'a\xf0\x9f\x98')`).

### 7. Time zones in the `get*` functions

`getHours('America/Sao_Paulo')` and the other accessors take a time zone
name, which cel-python hands to `pendulum.timezone`, that is to
`zoneinfo.ZoneInfo`. Before the final audit's FA-K-1, only UTC-like names
and the fixed-offset `Etc/GMT±N` zones were accepted, and zones with
daylight-saving rules were refused.

This is now resolved. `gen/gen-tz-tables.py` embeds the pinned reference's
own `tzdata` package (2026.3, IANA 2026c) in `Petrus.Cel.Tz.Tables`, so an
answer never depends on the tz database of the machine evaluating it.
`Petrus.Cel.Tz` resolves a key as ZoneInfo does with an empty `TZPATH`:

- the key validation and its three `ValueError`s;
- the dotted package import of the key's directories (`America.Argentina/Salta`
  and `America/__init__/Sao_Paulo` are zones too);
- `embedded null byte`, and the `Invalid TZif file` error of the package's
  other files (`zone.tab`, `__init__.py` ...);
- `utc` in any casing, and the `[+-]hh:mm` fallback with CPython's messages.

It reads a zone as C `zoneinfo_fromutc` does, through the transition table
and then the TZ string rule. `astimezone` also checks the intermediate UTC
value for overflow, as CPython does.

Evidence:

- the corpus groups `timestamp.zones` (24 zones × 23 instants, DST changes
  and the TZ-string era included), `timestamp.zone_keys` and
  `timestamp.zone_overflow`;
- the live differential in `test/Live.hs`. On every run, with a fresh seed,
  the reference reads every tzdata key, every directory and about 1 500 keys
  mutated from zone names, at random instants and on both sides of
  transitions from each zone's table and rule, about 18 800 readings in all.
  Haskell must answer every reading exactly as cel-python did.

## Open

### 2. Object identity is not tracked

CPython's `list.__eq__` and dict lookup first compare by identity, so the
same NaN object can equal itself inside a container. Haskell values have no
identity, so these shortcuts are never taken.

The only observable case is one NaN object reached twice inside a
container. A Petrus expression builds NaN only with `double('nan')`, and
each call gives a new object, so the case does not arise.

Source: `Petrus.Cel.Ops`.

### 3. Repeating a sequence beyond 2^31 elements

A plain Python string, bytes or list that leaks out of celtypes arithmetic
can be repeated with `*`. Past 2^31 elements, CPython tries the allocation,
and that fails with `MemoryError` or exhausts the machine. The Haskell
evaluator raises `MemoryError` at once, without allocating.

Source: `Petrus.Cel.Ops`.

### 4. `\C` in a regular expression

RE2's `\C` matches one byte of the UTF-8 encoding. Here it matches one code
point. The two differ only on non-ASCII text matched byte by byte.

Source: `Petrus.Cel.Regex`.

### 5. RE2's program-size limit is approximate

RE2 refuses patterns whose compiled program exceeds its size limit, for
example `\pL{500}`. The Haskell compiler estimates RE2's program size, so a
pattern very close to the limit can be accepted on one side and refused on
the other.

Source: `Petrus.Cel.Regex`.

### 6. Clock-dependent timestamps

In cel-python, two inputs read the current clock, so their results are not
reproducible:

- `timestamp('now')`;
- a time-only string such as `timestamp('12:00')`, which pendulum completes
  with today's date.

The Haskell evaluator refuses both with a `ValueError` that names the
reason. Petrus evaluation is deterministic: a guard or filter must give the
same answer on replay.

Source: `Petrus.Cel.Time`.

### 9. The reference's time zones depend on its host

The reference's answer to a zone name depends on the machine it runs on:

- **The host's tz database comes first.** ZoneInfo searches `TZPATH`, the
  host's `/usr/share/zoneinfo` and its siblings, before the `tzdata`
  package. So its answers follow the host's IANA release.
- **File systems differ.** On a case-insensitive file system (macOS by
  default), ZoneInfo opens `Europe/berlin` or `cet` as `Europe/Berlin` and
  `CET`. Only the final component is affected, because imports check the
  case of directories.
- **Imports leave files behind.** Once the `tzdata` packages have been
  imported, their `__pycache__` directories exist, and
  `Europe/__pycache__/...` names a resource that is not a zone.

petrus-cel answers as the reference does with an empty `TZPATH` on a
case-sensitive file system with no `__pycache__` in `tzdata`. That is the
pinned `tzdata` package and nothing else, the same everywhere. The
corpus is recorded that way (`zoneinfo.reset_tzpath(to=[])`), and the live
differential generates no case variants and no `__pycache__` keys.

Source: `Petrus.Cel.Tz`.

## By design

### 8. A diagnostic whose rendering raises: the specification over the reference

celpy renders a `CELEvalError` raised at a tree with `tree_dump`, and that
visitor pops an empty stack on some trees: an empty list or map literal as
an operand of a failing comparison or operator, such as `x.tags == []`
when `tags` holds a string, `x.tags + [] == 1` or `x.n > {}`. `repr()` of
the error then raises `IndexError("pop from empty list")`. The reference
builds its filter, guard and completion warnings with `{error!r}`
(`impetus/petrinet/enabledness.py`, `impetus/instance/__init__.py`), so the
`IndexError` escapes the enabledness or completion evaluation and the
Instance call fails.

The specification rules otherwise. `upstream/petrus/spec/firing-semantics.md`
("Evaluation errors in this pipeline are ruled", lines 36-48, [DR 2026-07-08
guard-filter-evaluation-errors]): a runtime evaluation error on a concrete
token means that binding is not satisfied, the candidate is skipped,
enablement computation continues, and the error is surfaced as a
diagnostic. The reference's crash is not a rule; it is celpy's `tree_dump`
bug reaching the warning's `repr`. So the port follows the specification:
`Binding.diagnostic` renders such an error without its tree, and the
kernel warns and reads the expression as not satisfied, as for any other
evaluation error.

The corpus still pins celpy's behavior exactly: `excReprStrict` reproduces
the raise, and the corpus checks it on every case whose rendering raises.
`KernelSeam` ("skips the binding when the reference's rendering of the
error raises") checks the kernel's skip and the diagnostic it surfaces.

Source: `Petrus.Cel.Value` (`excRepr`, `excReprStrict`),
`Petrus.Cel.Binding.diagnostic`.
