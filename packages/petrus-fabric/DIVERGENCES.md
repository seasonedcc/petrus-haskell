# petrus-fabric: divergences from `petrus.fabric`

The parts meant to match the pinned reference do match. They are checked
against the reference itself on one database:

- the envelope JSON, the canonical bytes, digests and ingress identities;
- the `impetus_fabric` schema (DDL text and catalog), its rows, statements
  and transaction discipline;
- the refusal categories, and the refusal texts where the spec quotes them;
- the `fabric.send` Activity profile;
- the demo's nets, records, events and printed lines.

The evidence is in [PARITY.md](PARITY.md). This file lists only differences
in the API surface, plus the places where the spec leaves a choice and the
port makes a different one than the reference.

The connection-level differences (text-format parameters and the others)
come from `petrus-postgres`. See
[its DIVERGENCES](../petrus-postgres/DIVERGENCES.md).

| # | Reference | Haskell | Why |
| --- | --- | --- | --- |
| 1 | `Envelope(...)`, `ReplyRoute(...)` and `Endpoint(...)` are frozen dataclasses. They validate in `__post_init__`, raise on a refusal, and offer `to_data()` and `from_data()`. | Smart constructors (`envelope`, `replyRoute`, `endpoint`) answer `Either FabricError`. The record constructors are not exported. Fields are read with record dot syntax (`e.sender`, `e.digest`, `e.ingressIdentity`). The conversions are `envelopeToData` and `envelopeFromData` (likewise for the other two types). | A value that exists has passed validation, and refusals are values. The payload's canonical bytes are computed once, at construction, and the digest is computed on first use and then kept. The reference recomputes both on each access. |
| 2 | Refusals are Python built-in exceptions: `ValueError`, `TypeError`, `PermissionError`, `LookupError` and `RuntimeError`. | One `FabricError` type with a constructor per category. Each constructor records the class the reference raises at that site (`pythonExceptionName`). Storage failures stay `Petrus.Postgres.PostgresError`, as psycopg's errors propagate in the reference. | fabric.md §12 makes only the category normative. `FabricError` declares the class it stands for (`IsPythonException`, petrus-json's open exception hierarchy), so every dispatcher, span and firing failure records a refusal raised inside an Activity exactly as the reference records its own: `kind` is the class, and `error` is `repr(error)` under the Local, Absurd and ZeroMQ custody workers or `str(error)` inline. |
| 3 | `PostgresFabric(connection, instance, credential)` is an object with methods. | `postgresFabric connection instance credential :: IO PostgresFabric`, and every method is a function that takes the client first (`submit client e`, `pending client 100`, `pruneAccepted client cutoff`). `fabricInstance` reads `client.instance`. `send` is the reference's alias of `submit`. | Haskell module style. The SQL, the `hmac.compare_digest` check, and the one-transaction-per-operation discipline on an autocommit connection are the reference's. |
| 4 | `FabricInbox(client, delivery_door)` duck-types both arguments: `client.pending` and `client.acknowledge`, and `door.deliver(source, tokens, identity=...)`. A door answer other than a firing outcome or a prior acknowledgement raises `TypeError`. | `FabricInbox {client :: InboxClient, door :: DeliveryDoor}`. `inboxClient` adapts a `PostgresFabric`. `engineDoor` and `engineInbox`, in the `petrus-fabric:engine` sublibrary, adapt an Engine. A door answers a `DoorAnswer`: `DoorFired` or `DoorPrior`, so it cannot answer another type. `engineDoor` refuses the Engine's scoped acknowledgement itself as `InvalidType` (the reference bridge's `TypeError`, same message), before the delivery is acknowledged, so `drain` fails at the same point. | The reference passes the Engine itself as the door. Here the adapter lives in a sublibrary, so the main library depends on no Engine or PostgreSQL package (the neutral-import test). The type rules out the answers the reference refuses at run time. |
| 5 | Some API arguments accept arbitrary Python objects, and a wrong type raises `TypeError`. That covers payloads containing host values (F-007), non-string keys (F-008), `pending(True)` (F-076), `acknowledge(..., occurrence=True)` (F-080) and a naive `datetime` cutoff (F-091). | **Type-enforced refusals.** Payloads are `Json` with `Text` keys. The limit and the occurrence are `Int`. A pruning cutoff is a `UTCTime`. None of these values can be passed, and [TypedSpec](test/Petrus/Fabric/TypedSpec.hs) checks each one against the real signature under deferred type errors. | The refusal happens at compile time instead of run time. The conformance twin answers these checks with an `InvalidType` refusal saying "type-enforced". |
| 6 | A string containing a lone surrogate is refused (F-005). | `Text` cannot hold a lone surrogate. `T.pack` replaces one with U+FFFD before any Fabric code sees it (TypedSpec, F-005). | The same type-level enforcement as row 5. A Python peer can never send one, because its own encoder refuses it. |
| 7 | U+0000 in a Fabric text or a JSON string is accepted at construction. It fails later, as storage: psycopg or the server refuses the NUL. | U+0000 is refused at construction (`InvalidValue "... must not contain NUL (U+0000)"`), so no statement is sent. | fabric.md §3.1 SHOULD, which F-004 accepts both ways ("refused at construction (preferred) or fails as storage, and no row is written"). The outcome is the same: no row is written, and the operation fails. |
| 8 | The canonical form is `json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)`. | `Petrus.Fabric.Canonical` is a dedicated encoder that writes exactly CPython's bytes. Its floats are petrus-json's shared CPython repr (`Petrus.Json.Float`, a port of the reference Ryu algorithm with CPython's rules: the rounding interval's ends are admitted when the significand is even, and exact ties are broken to even), the same spelling every petrus-json float path writes. Refusals fall back to petrus-json's general encoder for the refusal text. | The output is the same bytes. CanonicalSpec checks them against CPython over 50000 random doubles, 20000 large even-significand doubles, 5000 exact ties, 2000 subnormals, 10000 short decimals, the powers of ten and two, and escaped strings and keys, and against petrus-json's general encoder on generated values. The encoder exists to be faster than the general one on this one spelling. |
| 9 | Telemetry (`fabric_submitted`, `fabric_denied` and the others) goes to the process-wide `impetus` logger. | The same events and fields, emitted through `petrus-telemetry`'s `impetus` logger. | — |
| 10 | `scripts/cv5-fabric-demo.py` starts a disposable PostgreSQL container with docker when `--dsn` is not given. | `cv5-fabric-demo` requires `--dsn` and exits 1 without it. It also accepts `--parent-command` and `--child-command`, which run either role's subprocess with another implementation. Without them, the scenario is the reference's. | The test suites and CI provide a server (`PETRUS_TEST_POSTGRES`). The extra flags drive the split-role runs across implementations (F-107). |
| 11 | `petrus.fabric` has no `fabric.send` executor in the library. Each demo script defines its own `SendActivity`. | `Petrus.Fabric.Send` exports the §11 profile: `sendInvocation`, `sendActivity` and `sendResult`. The demo uses it. | This is an addition. It lets an Activity that a Python Engine requested be executed here, and the reverse. The result object and refusal texts are the demo's. |
