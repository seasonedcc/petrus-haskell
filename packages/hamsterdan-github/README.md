# hamsterdan-github

This package is Hamsterdan's GitHub App boundary, ported from
`upstream/hamsterdan` (`src/hamsterdan/github_app`) together with the parts of
githubkit, httpx, hishel and PyJWT whose behavior Hamsterdan can observe. It
contains:

- strict host configuration and the installations TOML;
- webhook signature verification and the durable SQLite inbox;
- the installation routing registry;
- the App JWT, installation tokens, and the startup check of the App's
  permissions, events, installations and repositories;
- a bounded REST, download and GraphQL transport;
- typed reads and writes for every GitHub API call in docs/hamsterdan.md §1.6:
  - pull requests, branch policy, reviews and threads, Actions runs and jobs;
  - Git blobs, trees and commits, and the GraphQL `updateRefs`
    compare-and-swap;
  - lookup-first comments, inline findings and review batches;
  - the rerun marker.

The port is byte-compatible with the pinned Python on the wire, in the SQLite
stores, and in every message Hamsterdan writes. The differential corpora
(9016 rows, generated by the committed scripts running the pinned Python)
prove it; see [PARITY.md](PARITY.md). The deliberate differences, none of
which touches a wire format, are in [DIVERGENCES.md](DIVERGENCES.md).

## The GitHub effect seam

All provider I/O crosses two seams, and tests replace either one.

1. **The capability records** in `Hamsterdan.GitHub.Models`. They are the
   seam the reference itself has (its `Transport` protocols):

   ```haskell
   data Transport = Transport
     { request :: Text -> Text -> Maybe [(Text, Json)] -> IO WireResponse
     , pages :: Text -> IO [[(Text, Json)]]
     }
   newtype BinaryTransport = BinaryTransport {download :: Text -> Int -> IO ByteString}
   data GraphQLTransport = GraphQLTransport
     { reviewThreads :: Text -> Text -> Integer -> IO [Json]
     , resolveReviewThread :: Text -> IO ()
     , compareAndSwapRef :: Text -> Text -> Text -> Text -> IO ()
     }
   ```

   The gateway, the publisher and the broker see only these records:

   - `githubTransport`, `githubDownloads` and `githubGraphQL` build the
     bounded production values;
   - `test/GitHubSpec.hs` builds fakes as plain record values;
   - the effects corpus replays recorded provider replies through a scripted
     `Transport`.

2. **The `Exchange`** in `Hamsterdan.GitHub.Http`, under the client stack:

   ```haskell
   newtype Exchange = Exchange
     {exchange :: forall a. HttpRequest -> (RawResponse -> IO a) -> IO a}
   ```

   - An `HttpRequest` is exactly what httpx would put on the wire: method,
     raw target, ordered lowercase headers and body bytes.
   - A `RawResponse` is the status, the raw header bytes and a chunk reader.
   - `newRealExchange` is the production exchange (http-client with TLS, no
     proxy, no redirects, no decompression, no timeout). The HTTP corpus and
     the client tests use a scripted exchange instead.
   - Everything above the exchange runs unchanged in tests: header decoding,
     `Content-Encoding`, the hishel cache, App/installation auth, the token
     cache, the metadata hook and the transport bounds.

The clock is part of `ClientOptions` too. The publisher takes its fence, fault
hook and retry delay as functions. No test makes a network call.

## Wiring a host

```haskell
{-# LANGUAGE OverloadedRecordDot #-}

import Data.Map.Strict qualified as Map
import Hamsterdan.GitHub
import Hamsterdan.GitHub.Gateway qualified as Gateway
import System.Environment (getEnvironment)

main :: IO ()
main = do
  config <- fromEnvironment . Map.fromList =<< getEnvironment
  clients <- githubAppClients config =<< defaultClientOptions
  -- Refuse to start unless the App, its installations and repositories are
  -- exactly what the configuration declares (throws ContractRefused).
  RegistrationInventory {installations = _portfolio} <- registrationInventory clients config
  -- One operation client per (installation, repository):
  client <- either (fail . show) pure (installationClient clients 44 [31])
  let transport = githubTransport client
  authority <- either (fail . show) pure (githubAuthority transport "owner/one" 7 (Just (githubGraphQL transport)))
  pull <- Gateway.pullRequest authority
  print pull.head
```

`openCustody` with `receive` (webhooks) and `openRegistry` with `route`
(admission routing) open the two SQLite stores under `config.statePath`, with
the reference's schemas, so a Haskell host can resume a Python host's state.

## Library choices

Each dependency was chosen so that the bytes on the wire and in the stores
can be controlled exactly.

- **HTTP: `http-client` + `http-client-tls`.**
  - Hamsterdan's requests must match githubkit/httpx byte for byte: header
    names, values and order, no `X-GitHub-Api-Version`, httpx's
    `accept-encoding`. Responses need httpx's semantics: no redirects
    followed, `Content-Encoding` decoded by the caller, bounded streaming
    reads, no timeout.
  - `http-client` sends the header list it is given. Through `responseOpen`
    and `brRead` it exposes the raw status, header bytes and body chunks,
    which is exactly the `Exchange` contract. Redirects (`redirectCount = 0`),
    decompression (`decompress = const False`) and the timeout are switched
    off per request.
  - Higher-level clients (`req`, `wreq`, the `github` package) add headers,
    decode bodies, follow redirects or model responses with aeson, and
    Hamsterdan would then have to undo each of those. docs/hamsterdan.md §3
    rules out the `github` package for this reason.
  - `http-client-tls` is the standard TLS manager for `http-client`.
- **JWT signing: `crypton` (`Crypto.PubKey.RSA.PKCS15`) and
  `crypton-x509-store`, not `jose` or `jwt`.**
  - RS256 is RSASSA-PKCS1-v1_5 with SHA-256, which is deterministic. The port
    spells the header (`{"alg":"RS256","typ":"JWT"}`) and the claims
    (`iss`, `iat`, `exp`, in PyJWT's order and compact form) itself, then
    signs them. The result is the same token bytes PyJWT produces for the
    same key and second. The HTTP corpus checks this on every App-authenticated
    request.
  - The JWT libraries (`jose`, `jwt`) serialize headers and claims through
    aeson, which decides member order and number spelling for us. `jose` also
    brings a much larger dependency surface.
  - `crypton-x509-store`'s `readKeyFileFromMemory` reads PKCS#1
    (`RSA PRIVATE KEY`) and PKCS#8 (`PRIVATE KEY`) PEM, as PyJWT's
    `load_pem_private_key` does.
  - `crypton` is the maintained successor of `cryptonite`, and it is already
    in this repository's dependency set.
- **HMAC: `crypton` (`Crypto.MAC.HMAC`, SHA256) with `ram`'s `constEq`.** These
  give the constant-time `X-Hub-Signature-256` comparison that githubkit makes
  with `hmac.compare_digest`. crypton's SHA-256 uses the ARMv8 SHA-2
  instructions, which keeps verification at Python's (OpenSSL's) speed or
  better (see [bench/RESULTS.md](bench/RESULTS.md)).
- **`zlib`** decodes `Content-Encoding: gzip` and `deflate` incrementally,
  through its low-level interface. That interface is needed to reproduce
  httpx's decoders exactly: the deflate decoder falls back to a raw stream
  only on the first chunk, and decode errors fall into the same exception
  family as httpx's.
- **SQLite: `direct-sqlite`.** The inbox and the routing registry must keep
  CPython `sqlite3`'s exact schema, pragmas, transactions and stored text. A
  thin binding gives that control without a mapping layer in between.
  `Hamsterdan.Sqlite` adds what the reference relies on:
  - the 5 s busy timeout;
  - `with connection:` transactions;
  - a lock and a statement cache.
- **TOML: `toml-parser` (pinned to 2.0.1.2).** It is a TOML 1.0 parser with
  exact acceptance, as strict as `tomllib`. It is pinned because the
  installations corpus (1500 files) depends on its exact acceptance.
- **JSON: `petrus-json`.** It reproduces CPython's `json` module for both
  parsing (`json.loads`, duplicate keys, the 4300-digit limit) and spelling
  (`separators`, `sort_keys`, `ensure_ascii`, `allow_nan`). Hamsterdan hashes
  and stores those exact spellings.
